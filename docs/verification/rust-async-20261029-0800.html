Rust 1.39：async / await 稳定

Rust 1.39 正式稳定 async 函数、异步块与 .await，让 Future 的组合有了直接语法。

为什么重要

编辑解读：它为 Future 组合提供接近顺序代码的表达方式，但把任务调度与 I/O 运行时选择留给生态，并不自动带来多线程或性能提升。

编辑概述；具体事实见下文及其来源。

背景：先稳定 Future，再交付语法

2019年7月4日的 Rust 1.36 先稳定 Future trait，公告明确让库和生态为 async / await 做准备。11月7日，1.39 才稳定 async fn、async 块与 .await。二者不是同一天落地；Rust 2018 是使用这些语法的版次门槛，不代表语法已在2018年稳定。315原文定位：1.36 → The Future is here!；1.39 → The .await is over；Reference → 2018 Edition differences

机制：调用不等于启动任务

同期说明强调，调用 async 函数只是取得尚待执行的 Future，不会自行调度它。执行器驱动外层任务，.await 组合内部计算；当 Future 尚不能推进时，可交还控制权。后缀 future.await 还可接 ? 传播错误。这里的“惰性”不能理解成每一次 await 都必然暂停。46原文定位：Async-await: a quick primer；Zero-cost futures；Primer → executor 与 .await

边界：语法、执行器与并行分开

1.39 的稳定化不是把 Tokio 等运行时一并纳入标准库；同期文章把各运行时适配及其计划单列为生态工作。教程区分 block_on 阻塞当前线程与 .await 等待，且展示同一线程上的多任务并发。因此，加上 async 不等于启动新线程，也不保证应用里的阻塞调用被自动改造为异步 I/O。462原文定位：The Async Ecosystem → Async Runtimes；Major developments in the async ecosystem；Primer → block_on 注释与 join! 示例

编辑分析：沿三层阅读，而非只记关键字 · 编辑解读

建议先看发布公告确认“何时稳定”，再看同期设计解释“Future 如何组合”，最后用教程检查“谁驱动任务”。把顺序等待、并发和多线程并行分别记录，才能理解后续运行时为何仍有不同调度取舍。这是编辑学习路径，不是某个运行时更快或适合所有工作负载的结论。

版本变化

比较基线：Rust 2018 发布时尚未稳定的 async / await

回看已收录基线：Rust 2018 edition 发布

  • async fn 与 async 块稳定
  • .await 组合 Future
  • Rust 2018 的借用检查迁移警告升为错误

边界：调用 async 函数返回待驱动的 Future，不代表计算已自动完成；借用检查修正也可能暴露旧代码问题。
